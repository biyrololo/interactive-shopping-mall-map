# Интерактивная 2D/3D карта этажа торгового центра

Интерактивная карта этажа торгового центра на 100 объектов, разработанная на чистом JavaScript (ES6+ модули) с использованием Three.js и WebGL.

Проект разработан без использования UI-фреймворков.

---

## Запуск проекта

### 1. Установка зависимостей
```bash
npm install
```

### 2. Запуск локального сервера разработки
```bash
npm run dev
```
Приложение доступно по адресу `http://localhost:3000`.

### 3. Запуск автоматических тестов
```bash
npm test
```
Тест валидирует:
- генерацию ровно 100 объектов;
- наличие обязательных базовых магазинов (shop_001 - shop_005);
- математическое отсутствие пересечений между всеми объектами (0 коллизий);
- корректность поиска по ID со сложностью O(1);
- корректность обработки граничных случаев с длинными названиями.

### 4. Сборка для публикации (Production Build)
```bash
npm run build
```
Сборка сохраняется в директорию `dist/` с относительными путями (`base: './'`).

## Управление картой

- Клик левой кнопкой мыши (ЛКМ) по магазину или плашке: выбор объекта.
  - В консоль браузера (`DevTools -> Console`) выводятся данные: `ID`, `Name`, `Position (x, y, z)`.
  - Магазин выделяется янтарным контуром, открывается карточка с габаритами и категорией.
- Наведение курсора (Hover): плавная подсветка здания (+40% яркости) и синий контур граней с анимацией ~200 мс, увеличение плашки на 15%.
- Пробел (Space) или кнопка переключения в верхнем правом углу: плавный переход между 3D-видом и 2D-планом сверху.
- Вращение, зум и панорамирование:
  - В 3D: ЛКМ вращает сцену, ПКМ панорамирует, колесо мыши масштабирует.
  - В 2D: вращение заблокировано строго сверху, доступны перемещение и зум.
- Кнопка с иконкой тега в правом нижнем углу: переключение режима отображения подписей (крупный экранный размер / компактный фиксированный размер).
- Поисковая строка: фильтрация магазинов по названию или ID с автодополнением и центрированием камеры на объекте.
- Esc: сброс текущего выделения.

## Алгоритм размещения 100 объектов без пересечений

Алгоритм реализован в модуле `src/layout.js`:

1. 100 магазинов упорядочиваются по торговым рядам (10 рядов по 10 магазинов в каждом).
2. По оси X магазины размещаются последовательно с учетом индивидуальной ширины каждого павильона и безопасного интервала:
   $$X_{i+1} = X_i + \frac{W_i}{2} + \text{gapX} + \frac{W_{i+1}}{2}$$
   где $\text{gapX} = 1.2$ м.
3. По оси Z каждый ряд отделен проходом $\text{aisleGap} = 3.5$ м, рассчитанным от максимальной глубины магазинов текущего ряда:
   $$Z_{\text{row}+1} = Z_{\text{row}} + \max(\text{depth}_{\text{row}}) + \text{aisleGap}$$
4. После завершения раскладки весь массив координат сдвигается так, чтобы центр масс этажа находился в начале координат $(0, 0, 0)$.
5. Контроль коллизий: функция `checkCollisions` выполняет попарное сравнение 2D AABB (Axis-Aligned Bounding Box) всех 100 объектов:
   $$\text{Overlap} \iff (|x_A - x_B| < \frac{w_A + w_B}{2} - \varepsilon) \land (|z_A - z_B| < \frac{d_A + d_B}{2} - \varepsilon)$$
   Результат проверки: 0 пересечений.

## Граничный случай: длинные названия магазинов

В датасет включен тестовый магазин с длинным названием более 70 символов (`shop_006`: «Флагманский гипермаркет электроники и бытовой техники «М.Видео-Эльдорадо»»).
- В модуле `src/labels.js` ширина текста измеряется через метод `ctx.measureText`.

- При клике на объект его полное имя без сокращений отображается в карточке магазина.

## Архитектура и оптимизация (Раздел 4 ТЗ)

### 1. Как оптимизировать отображение текстовых подписей, если объектов станет 1000+?

При переходе от 100 к 1000+ объектам рендеринг через отдельные `CanvasTexture` на каждый объект создает слишком много вызовов отрисовки (Draw Calls) и расходует видеопамять. Решения для масштабирования:

1. **SDF (Signed Distance Field) / MSDF Font Atlas:**
   Все глифы шрифта запекаются в единую растровую SDF-текстуру (атлас). Каждая подпись строится из набора квадов, привязанных к координатам атласа. Это позволяет отрисовать все 1000+ подписей за **1 Draw Call** через единый `InstancedMesh` или `BatchedMesh`. Текст сохраняет резкость при любом приближении камеры без перегенерации текстур.
2. **Frustum Culling и Distance Culling:**
   Отсечение невидимых подписей. Проверка положения bounding sphere каждого текста относительно пирамиды видимости камеры (`frustum.intersectsSphere`). Подписи, находящиеся за пределами экрана или дальше заданного радиуса, исключаются из рендера на GPU.
3. **LOD (Level of Detail) и Decluttering (разрежение):**
   Иерархическое отображение в зависимости от высоты камеры:
   - при сильном отдалении отображаются только крупные якорные зоны (Фуд-корт, Супермаркет);
   - при приближении открываются подписи средних бутиков;
   - детекция наложений на 2D-экране: если две подписи перекрывают друг друга, менее приоритетная скрывается.

### 2. Если геометрию магазинов объединить в один меш (InstancedMesh / BatchedMesh), как обрабатывать клики?

При объединении геометрии в единый меш стандартная проверка отдельных объектов не подходит. Используются два подхода:

1. **Использование `intersection.instanceId` в Three.js Raycaster:**
   Three.js поддерживает рейкастинг по `InstancedMesh`. Метод `raycaster.intersectObject(instancedMesh)` возвращает структуру, содержащую поле `instanceId` (индекс экземпляра, в который попал луч). Данные магазина по этому индексу извлекаются из связного массива за $O(1)$ без необходимости разбиения геометрии.
2. **GPU Color Picking (рендеринг в Offscreen Framebuffer):**
   Каждому магазину назначается уникальный целочисленный идентификатор, закодированный в RGB-цвет (24 бита дают до 16.7 млн ID).
   - При клике сцена отрисовывается в скрытый `WebGLRenderTarget` размером 1x1 пиксель прямо под позицией курсора с простым шейдером, выводящим ID-цвет.
   - Метод `gl.readPixels` считывает 4 байта цвета, которые мгновенно декодируются обратно в числовой ID объекта.
   - Сложность проверки: $O(1)$, производительность не зависит от количества полигонов и числа объектов в сцене.

### 3. Какую структуру данных в JS лучше использовать для хранения данных, если нужен быстрый поиск по ID и координатам?

1. **Для поиска по ID: `Map<string, PlaceData>`**
   Хэш-таблица на базе нативного `Map` обеспечивает доступ со сложностью **$O(1)$** в среднем и в худшем случае. Ключ - строковый или числовой `id`, значение - ссылка на объект данных.
2. **Для поиска по координатам (X, Z): `2D Spatial Hash Grid` (пространственная сетка)**
   Плоскость этажа разбивается на регулярную сетку ячеек фиксированного размера (например, $10 \times 10$ м).
   - Ключ ячейки вычисляется математически за $O(1)$:
     ```javascript
     const cellX = Math.floor(x / cellSize);
     const cellZ = Math.floor(z / cellSize);
     const key = `${cellX}:${cellZ}`;
     ```
   - В каждой ячейке хранится массив ID магазинов, пересекающих данную ячейку.
   - При поиске точки $(x, z)$ вычисляется ключ ячейки, и проверка выполняется только для 1-3 объектов внутри нее вместо перебора всей 1000.
3. **Альтернатива для неравномерных распределений: `2D R-Tree` (библиотека RBush) или `Quadtree`**
   Древовидные структуры подходят при сильном разбросе размеров магазинов (от мелких островков 2x2 м до гипермаркетов 50x50 м). Сложность пространственного поиска составляет $O(\log N)$.

### 4. Реализация переключения 2D / 3D: плюсы и минусы подходов

В проекте реализовано переключение между перспективным ракурсом и ортографическим планом этажа.

#### Подход 1: Две камеры (PerspectiveCamera + OrthographicCamera) - [выбран в проекте]
- **Плюсы:**
  - В 2D получается честный архитектурный чертеж этажа: параллельные линии не сходятся в перспективе, масштаб одинаков по краям и в центре экрана, боковые грани стен не создают оптических искажений.
  - В 3D сохраняется естественное перспективное восприятие глубины пространства.
- **Минусы:**
  - Необходимость точной геометрической синхронизации видимого поля обзора при переходе, чтобы не происходило скачка масштаба:
    $$D = \frac{\text{frustumSize} / \text{zoom}}{2 \cdot \tan(\text{fov} / 2)}$$
  - Необходимость переключения целевого объекта в `OrbitControls`.

#### Подход 2: Одна перспективная камера (наклон и полет камеры строго в зенит)
- **Плюсы:**
  - Меньше кода: не нужно создавать второй объект камеры и переключать управление.
  - Нет граничного момента передачи фокуса между разными типами матриц проекции.
- **Минусы:**
  - Это не настоящий 2D-план: из-за конуса видимости (FOV) объекты на краях экрана видны под углом, проявляется параллакс и просматриваются боковые стены павильонов.
  - Если приблизить FOV к нулю (эмуляция ортографии через малый угол и большое расстояние), падает точность буфера глубины (Z-fighting) и ухудшается управляемость вращением.
